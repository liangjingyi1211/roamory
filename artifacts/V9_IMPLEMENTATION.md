# V9 多意图编辑交付说明

按仓库中的 `Roamory_V9_Codex_Prompt.md` 实施，不新增 Agent、依赖、数据库或地图 UI。

## 修改文件

- `roamory/assistant.py`：解析 1–5 个有序意图、预检重叠范围、逐步执行、对象级补丁校验、最终范围和时间冲突检查、批量摘要及失败项提示。
- `roamory/storage.py`：抽取无数据库访问的 `apply_patch_in_memory`；`save` 支持显式预期版本并返回实际保存的版本；旧 `apply_scoped_patch` 保留为兼容包装。
- `tests/test_batch_edits.py`：新增 23 项批量执行、原子性、顺序、范围、解析和日志失败测试。
- `tests/test_assistant.py`：把旧的“两项意图非法”断言更新为“六项意图非法”，保留旧单操作回归。
- `README.md`：更新多操作示例、顺序、失败语义和边界。

## 调用与提交边界

`assistant_edit` 读取数据库行程并检查客户端版本 → `parse_edit` 返回有序意图 → `validate_batch_conflicts` 根据日期、槽位和稳定对象 ID 预检 → `execute_edit_batch` 深拷贝行程 → 逐项重新定位、生成并校验补丁 → `apply_patch_in_memory` 应用到副本 → 最终校验 → `save(expected_version=base.version)` 一次保存。

后续操作看到之前已应用补丁的工作副本。检索和补丁构建另外拿深拷贝，避免副作用污染工作状态；补丁中的可变值也深拷贝。

餐次重复编辑、整天重规划与该日局部修改、同类重规划与局部编辑重叠会要求澄清。不同既有景点可以按稳定 ID 分别替换；景点增加必须保留全部原景点，单项替换不能改动其他景点。字段白名单逐项检查，最终还检查日期及业务字段变更的授权并集。

所有网络操作均在 SQLite 写事务外完成。`TripStore.save` 在 `BEGIN IMMEDIATE` 事务中读取版本，核对预期版本及计划版本，写入完整 JSON，版本仅增加一次。行程已删除时不会重新创建。批量循环不调用会写库的 `apply_scoped_patch`，任意一步失败均不会提交前面的补丁。

单操作仍用同一执行器。响应保留 `updated_day_id`、单操作摘要字段，新增 `updated_day_ids` 和 `summary.operations`；已有 Streamlit 消息展示和完成后刷新无需改动。

## 可用示例

1. “把第二天午餐换成附近的日料，再给第三天增加一个博物馆。”两项按序处理，均通过后只保存一次；第二项失败则第一项也不保存。
2. “换第一天早餐和晚餐，午餐保持不变。”生成两个餐次操作，午餐、其他日期和景点保持原状。
3. “把第二天的国家博物馆换一个景点，再换第二天附近的午餐。”目标能唯一定位时，餐厅检索使用更新后的景点位置。

## 保守边界

- 未实现前序结果引用协议。对于“再把刚才新选的那家店换掉”等无法可靠定位的表达，解析器应要求澄清，不得伪造 ID。自然语言解析仍受模型准确性影响。
- 对重复或重叠修改不采用后写覆盖；同一天多次增加景点暂按重叠范围处理，建议拆分发送。
- 新增明确时间冲突会阻止整批提交；旧冲突和时间待安排提示可以保留。未增加交通耗时、路线最优或全局约束求解能力。
- 保持既有行为：用户明确输入店名时保存未核实的名称，不伪造 Place ID；推荐模式继续执行真实候选校验及已有餐饮规则。
- 未增加批量撤销、历史版本或自动依赖重排序；用户明确叙述顺序即执行顺序。
